# Backlog / considered-but-not-built

Ideas that came up during development, were deliberately evaluated, and either deferred or rejected. Kept here so they aren't re-litigated from scratch in a future session — if you're considering one of these, read the reasoning first and only revisit if the stated condition has changed.

## Deferred

- **Drop the pre-2026.10 typing workarounds once the minimum Home Assistant version reaches 2026.10.** That release switched form schemas to probatio (aliasing `import voluptuous` to it at runtime) and moved `BinarySensorDeviceClass` to `homeassistant.components.binary_sensor.const`. The minimum (2026.8) has neither, so `config_flow.py` keeps voluptuous and passes schemas through `_form()`, and `binary_sensor.py`'s import carries a `type: ignore`. At 2026.10+: build the schemas with probatio directly, delete `_form()`, and import from `binary_sensor.const`. Likewise `number.py`'s `async_entity_id_changed` ignore once the minimum reaches 2026.11 (where it becomes an ordinary `@override`). See `docs/quality-scale.md`.

- **Inline release-notes body content (not just a link) for floating-tag images with no Dockhand `newerVersion` suggestion** — e.g. AudiobookShelf (`ghcr.io/advplyr/audiobookshelf:latest`) shows a "View release notes" link (via `_pending_update_changelog_section()`'s empty-`versions` call) but not the "What's Changed" body content Authentik gets when Dockhand's semver engine finds a concrete `newerVersion` target. Root cause is structural, not a bug: Dockhand's `checkNewerVersion()` explicitly skips floating tags ("Floating tag -> nothing to compare, and we skip the registry call entirely", `semver/check.ts`), so it never produces a target tag for these images, and `version-notes` can only fetch notes for tags it's given by name — there's no "everything newer than X" call on Dockhand's side. `resolveAndFetchReleaseNotes`'s wanted-list matching is also why the empty-`versions` call deliberately returns `notes: []` (short-circuits before any network call) even for a confident source. The fix would be a client-side release fetch: use the `source`/ `changelogUrl` Dockhand's empty-`versions` call already resolves for us (confident sources only — GitHub or Gitea/Forgejo) to hit that forge's releases API ourselves, filter to releases newer than the container's OCI `image.version` label, and render their bodies the same way `_semver_advisory_section()` does. **Scope this narrowly if it's ever built**: only do the "everything newer than installed" fetch when the container's raw image tag has NO digits at all (`latest`, `stable`, `edge`, `nightly`, `main`, and similar) — a tag with any digit in it (`v3`, `16-alpine`, a partial CalVer pin like `2026.2`) still imposes a ceiling Install can never cross (Traefik's `v3` will never become `v4` via Install), and correctly bounding "newer than X" to that ceiling means reimplementing Dockhand's own flavor/major-bump constraint logic (`tag-parser.ts`) ourselves — real duplicated complexity, and exactly the kind of "displayed content doesn't match what Install can deliver" mismatch this integration has gone out of its way to avoid elsewhere (see the hasUpdate-vs-newerVersion precedence in `update.py`'s module docstring). Confirmed with the maintainer directly (a real example: an Authentik container with both an actionable same-tag update AND a newerVersion suggestion requiring re-pinning) that showing inline notes for anything beyond a genuinely ceiling-free tag is not acceptable. Also worth weighing before building: unauthenticated GitHub is 60 req/hour, shared across every zero-digit-tag container a user checks release notes for in a session — Dockhand's own server-side fetch has the same limit but at least centralizes it per-Dockhand-instance rather than per-HA-instance. Deliberately not built for the 1.10.0 release — maintainer wants to see whether Dockhand's own semver/release-notes feature grows to cover this (e.g. extending `newerVersion` detection to floating tags, or a "since version X" mode on `version-notes`) before duplicating any of that logic client-side. Revisit after a few more Dockhand releases, or sooner if Dockhand ships something that makes this moot or easier.

- **Moving a standalone container to a newer version tag** (an image pinned to `nginx:1.27` when Dockhand suggests `1.28`). Open for the maintainer to decide (2026-11-09). Compose-managed containers stay out of scope for good: the compose file is the user's own, and editing it out from under them is a trust problem. A container created with `docker run` or in Dockhand's own UI has no file to edit, and Dockhand's `POST /api/containers/{id}/update` (what `dockhand.recreate_container` already calls) takes the image to recreate with, so Install could recreate it on `newerVersion`'s tag. Questions to settle first: how to tell a standalone container reliably (no `com.docker.compose.project` label), whether this belongs on Install (which today only ever keeps the tag) or a separate action, how to present the version jump (often a breaking change, unlike a same-tag update), and how it interacts with Dockhand's minimum image age and vulnerability blocking. Dockhand's own UI only offers the suggestion as a badge with a link to release notes.
- **Re-checking a container right after Install so a "newer version tag" suggestion reappears immediately.** When a pinned image has both an installable same-tag update and a `newerVersion` suggestion, applying the update makes Dockhand delete that container's `pending_container_updates` row (`removePendingContainerUpdate()` in `batch-update-stream`), taking the suggestion with it. With `enable_precise_updates` on, our post-install Tier 2 refresh brings it back right away; with it off, the entity reads as up to date until Dockhand's next scheduled check or a manual "Check for updates" press. The only way to close that gap today is an environment-wide `check-updates` POST after every Install — Dockhand has no single-container check endpoint (confirmed against Dockhand's `src/routes/api/containers/`, 1.0.49-dev). Deferred by the maintainer during 1.10.1: a registry check of every container in the environment on every single update is too much load for the value. Revisit if Dockhand adds a per-container update check.

- **Proper destination-level device grouping for `repo_prune`/`repo_check`/ `repo_verify` schedule types.** Discovered during the 1.9.0 Schedules device-hierarchy work by reading Dockhand's actual `/api/schedules` source (`Finsys/dockhand`, currently 1.0.39 — two patch releases ahead of the 1.0.37 this integration was last fully reviewed against). These are backup *destination*-scoped maintenance jobs (prune/check/verify policies on a configured backup destination), not environment-scoped and not truly "system" either (`isSystem: false`, but `environmentId: null` — a third bucket distinct from both env-scoped schedules and genuine system jobs like `system_cleanup`). Not yet seen in a live Dockhand instance (no backup destinations configured at review time), so unconfirmed whether they're commonly used. For 1.9.0 they're handled safely but generically — `environmentId: null` routes them to the flat `schedules_hub` alongside real system jobs, same as before this rework, just without a dedicated "Destinations" grouping of their own. Revisit if/when backup destinations with these policies show up in practice and a dedicated group device (`_destination_group_device`, parented directly under the hub rather than an environment) seems worth the added complexity. The `backup` schedule type (destination-linked but genuinely environment-scoped via `config.environmentId`) is unaffected — it already groups correctly under its owning environment's Schedules group like any other env-scoped schedule.

- **Group `enable_update_entities`/`enable_precise_updates` with HA's `section()`.** Tried twice in the 1.8.1 cycle: the fields inside showed raw keys. The cause is now known (HA 2026.8 frontend, `show-dialog-options-flow.ts`): a field inside a section is labelled from `options.step.<step>.sections.<section>.data.<field>`, neither of the places tried. The entity sections (architecture §10) use that. Revisit the grouping if the flat form gets crowded.

- **Runtime controls: Block I/O (`Blkio*`) fields.** Left out of the first pass — low value for home-lab use, and real complexity (per-device weight maps, not scalars like the other runtime controls). See `docs/update-runtime-design.md` for the full design rationale.

- **`/api/system?env=X` for richer host/Docker info.** Returns `docker{version,apiVersion,os,arch,kernelVersion,serverVersion,connection}`, `host{}` (from Docker's own `/info`, not Node `os.*`), `runtime{}` (Dockhand's own process info), `database{}`, and `stats{}` — deliberately do **not** use `stats`, `/api/dashboard/stats` is more complete. Most of this overlaps what `/api/host` already gives us (platform, arch, Docker version). The two genuinely new fields (`apiVersion`, `kernelVersion`) aren't available anywhere else, but the endpoint is heavy server-side — it also fetches full container/image/volume/network lists just to compute `stats` we'd ignore — and can't replace `/api/host` (missing `hawserVersion`, `uptime`), so using it would be a net-new API call just for those two fields. Revisit if Dockhand ever adds a lighter-weight version of this endpoint, or if it becomes more/less inclusive.

## Waiting on Dockhand

Requests filed with Dockhand, and what to change here when each is answered. At each backlog or upstream review, check whether they're still open, released, or turned down (`gh api "search/issues?q=repo:Finsys/dockhand+is:issue+author:raetha"` lists them), and update or remove the entry.

- **Hidden helper containers** ([Finsys/dockhand#1911](https://github.com/Finsys/dockhand/issues/1911)). Dockhand's short-lived helpers (vulnerability scans `dockhand-grype-…`/`dockhand-trivy-…`, backup probes and helpers, created by `runContainerWithStreaming` in `src/lib/server/docker.ts`) carry only `dockhand.notify=false`, so `/api/containers` lists them while they run. A poll or a live-feed refresh that lands during a scan creates their entities, the next one removes them, and the statistics they leave behind show up as orphaned-statistics repairs in Spook. The request asks Dockhand to label them `dockhand.hidden=true` (or a helper label that `/api/containers` also filters). **If accepted:** nothing to build, since the integration lists containers through `/api/containers`; confirm on a release with the label that a scan no longer creates entities, then drop this entry. **If turned down (fallback):** skip containers whose name starts with one of Dockhand's own helper prefixes (`dockhand-grype-`, `dockhand-trivy-`, `dockhand-probe-`, `dockhand-backup-`, `dockhand-restore-`; `hooks.server.ts` matches scanner containers by the same prefixes) *and* that carry `dockhand.notify=false`, in one helper in `helpers.py` used wherever container entities are created. Both conditions together, so a user's own container named `dockhand-…` is never skipped. Scanner version checks (`dockhand-<scanner>-version-…`, created by `runContainer`) carry no labels at all, so the fallback either matches them by name alone or leaves them, since they exit within seconds. Rejected alongside: clearing statistics when a container is removed, which would also wipe the history of real containers that are recreated.

- **The new image's version for floating-tag updates** ([Finsys/dockhand#1501](https://github.com/Finsys/dockhand/issues/1501), with a comment from the owner asking for it in the API; raised here in #79 and #39). For an update on `:latest` or another floating tag, Dockhand knows only that the digest changed; the new image's `org.opencontainers.image.version` label is in the config blob its minimum image age check already downloads (`registry/image-age.ts`), digest-verified. **If Dockhand exposes it** (in `GET /api/containers/pending-updates` and `check-updates` results): use it as the update entity's `latest_version` (the installed side already reads the running container's label, `_image_version_label()` in `helpers.py`), and fetch release notes for it through `version-notes` like a semver update, so the update dialog shows the notes for exactly the image Install pulls; without a label, keep today's behavior. Answers #39 (a version instead of a digest) and #79 (release notes) without the integration contacting registries or GitHub. **If only Dockhand's UI shows it:** nothing to do here; ask again for the API field.

- **Self-update check for Hawser-only installs** ([Finsys/dockhand#1897](https://github.com/Finsys/dockhand/issues/1897)). Asks `/api/self-update/check` to fall back to its version-only comparison when Dockhand can't inspect its own container, as it does when it has none. **If accepted:** `_dockhand_host_candidates` in `coordinator.py` skips the check when no socket or direct environment holds Dockhand's container; drop that gating for Dockhand versions that answer `versionOnly`, so the Dockhand device's update entity exists for Hawser-only installs (feature-detect from the answer, not the version). Update README's note on that entity ("not when Dockhand reaches its hosts only through Hawser") and the self-update part of `docs/architecture.md`. The owner's own install is Hawser-only, so it can be tested there.

- **Poll event collection drops events** ([Finsys/dockhand#1886](https://github.com/Finsys/dockhand/issues/1886)). In Poll mode each poll reads only the last 30 seconds of Docker events, whatever the interval. **If fixed:** events in Poll mode arrive late but all arrive, so reword the `event_collection_poll` repair issue (every locale) and the README's Known limitations line and Data Updates paragraph to say only that events are delayed; whether the repair is still worth raising at all is then the owner's call. If Dockhand fixes it with `since = now - interval` instead, small gaps remain: keep a softened warning.

- **Disk usage on every stats request** ([Finsys/dockhand#1885](https://github.com/Finsys/dockhand/issues/1885)). `GET /api/dashboard/stats`, which the fast poll reads every 60 seconds, runs Docker's `system df` each time. **If Dockhand caches it** (the proposal: the stream endpoint's 5-minute cache): nothing to change, though the disk usage sensors then move at most every 5 minutes; say so in the README's disk usage rows. **If Dockhand adds an opt-out parameter instead:** pass it on the fast poll and read disk usage from `/api/system/disk` on the slow poll, keeping the same sensors and unique IDs.

## Rejected

- **Removing precise updates (`DockhandUpdateCoordinator`, Tier 2 / `CONF_ENABLE_PRECISE_UPDATES`).** Kept on purpose (Raetha, 2026-10-15): it's the only way to see that a system container (Dockhand itself, a Hawser agent) has an update. Dockhand never persists a `pending_container_updates` row for a system container — both `env-update-check.ts` (`if (isSystemContainer(imageName)) continue`) and the check-updates route skip writing it — so the always-on Tier 1 `pending-updates` poll can never report one; only Tier 2's in-memory copy of the raw check-updates response does (confirmed live: with precise updates off, those entities always read as up to date). For ordinary containers Tier 2 adds no new signal since 1.10.0 — Tier 1 carries the same registry result from Dockhand's own scheduled check. Revisit only if Dockhand starts exposing system-container update status through a stored, pollable endpoint. Precise updates also drives the self-update check that reports a newer release for a version-pinned Dockhand (#48).

- **Running a command inside a container from HA** (Dockhand 1.0.49+'s `POST /api/containers/{id}/exec/run`, which runs a short command and returns stdout, stderr and the exit code). Too powerful to trigger from HA directly for now — anything that can call an HA action could run arbitrary commands in any container. Only worth revisiting as part of a deliberate, opt-in "advanced features" set (off by default, clearly warned, ideally admin-only), never as an ordinary entity or action (Raetha, 2026-10-14).

- **Activity stats `byAction` breakdown as a separate sensor.** Tried and reverted during 1.8.0 development as a pure duplicate — the existing `DockhandEnvActivityEventsSensor` already has `today`/`total`; `byAction` (from `GET /api/activity/stats`) could be added as an *attribute* on that existing sensor if wanted later, but does not warrant new entities.

- **Config-sets** (Dockhand's reusable env-var/label bundles for stack deploys). Reviewed and deliberately not implemented — no live state, pure deploy-time template metadata, nothing maps to an HA entity concept.

- **Two-tier "gentle Deploy / forceful Update" buttons, symmetric across internal and git stacks.** Not achievable — see `docs/architecture.md` §6 for why (no per-call pull override exists for git stacks at all). Went with one Deploy/Redeploy button per stack type instead, each mirroring Dockhand's own default UI behavior as closely as possible for that type.

- **Stack/container/image/volume/network `configuration_url`s stay pointed at the generic list pages** (`/stacks`, `/containers`, `/images`, etc.), not deep-linked to a specific item, unlike the environment device's settings link (which does deep-link, per `dashboard-header.svelte`'s `goto` call). Checked: these pages do support a `?search=<name>` query param that filters the list client-side, but there's no URL-level environment-scoping anywhere in Dockhand's frontend (`$currentEnvironment` is a plain client-side store, never synced to/from the URL) — a `?search=` link would silently show wrong or empty results if the environment currently selected in Dockhand's own UI doesn't match the one the link was generated for. Not worth the confusion for an imprecise deep link; revisit if Dockhand ever adds env-scoped URLs.
